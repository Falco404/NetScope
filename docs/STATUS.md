- **#37 SQLite threading (part 1 of 2)** (PR #57, merged `14d1139` 2026-11-24): the store keeps **one connection per thread** (`threading.local`; `store.conn` is a property) instead of one shared `check_same_thread=False` connection. A shared connection let a request thread read *and commit* the scan thread's open transaction — `set_device_name`'s `commit()` published a half-written `save_scan`, and readers could see a `scans` row with zero `scan_devices` rows. Each connection now sets `foreign_keys`, `journal_mode=WAL` and `busy_timeout` (per-connection pragmas); all writes go through `_write_txn()` (one lock + rollback on failure, so a failed write never leaves an open transaction behind). 114 tests pass (3 new in `tests/test_store.py`, all proven RED against the old code), ruff clean.

The UI status line reads e.g. `running — pass 1/2 (discovery) — 7 host(s) found`, and the bar is computed by a `barWidth()` helper (discovery fills the left half by elapsed-vs-per-pass-limit; services fills the right half by `hosts_in_phase / hosts_found`) — the old hardcoded `60%` is gone. 119 tests pass (5 new: 3 in `tests/test_scanner_engine.py`, 2 in `tests/test_api.py`, 1 guard in `tests/test_frontend_xss.py`, all proven RED against the old code), ruff clean.
- **#38 hostname ambiguity (`blocked.local`)** (PR #60, merged `45c6722` 2026-11-25): Falco's no-admin LAN scan showed **nine devices all named `blocked.local`** and a diff saying `blocked.local appeared` twice — nmap's reverse-DNS (PTR) name was identical for every IP because the LAN resolver answers every PTR query with the same name (a DNS sinkhole, most likely Atom's Pi-hole). - **#38 load nmap's own `nmap-mac-prefixes` file** (PR #64, merged `ef0faba` 2026-11-25): `netscope/vendor_registry.py` gained `load_mac_prefixes(path)`, `find_mac_prefixes_file()` (nmap's own search order: `$NMAPDIR`, then the directory holding the nmap executable — on Windows `C:\Program Files (x86)\Nmap`) and `load_default_mac_prefixes()`; `main()` calls it before the store exists and prints which registry is in effect (`Vendor registry: 52085 MAC prefixes from C:\Program Files (x86)\Nmap\nmap-mac-prefixes` vs `Vendor registry: 5 built-in prefixes (no nmap-mac-prefixes found — install nmap or set NMAPDIR)`). Lookups now try the longest registered prefix first. Comment lines are not entries: the header's `# Nmap additions to this file:` / `# 525400, B0C420, DEADCA, 00FFD1, 080027,` would otherwise invent vendors for those five prefixes.
